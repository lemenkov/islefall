# NetStorm data formats

Reverse-engineered descriptions of the data files shipped with
*NetStorm: Islands at War* (Titanic Entertainment, 1997). Nothing here comes
from original sources or documentation; everything was derived from the files
in the game's `d/` directory and verified by decoding and rendering them.
Field names are ours.

All integers are little-endian. Offsets are given in hex.

## `_shapes.shp` sprite cache

`d/_shapes.shp` (6,237,352 bytes in the 8.2 release) holds every in-game
sprite as run-length-encoded 8-bit indexed frames. It is a cache generated by
the game from GIF sources that are *not* shipped, so it is the only source of
sprite pixels.

### Overall layout

```
+--------------------------------------------------+ 0x0
| container 0   ('1.10', count, count x entry)     |
| container 1                                      |
| ...                                              |
| container 118                                    |
+--------------------------------------------------+ 0x8498  (table end)
| frame records, back to back, in no particular    |
| order, each ending with a 36-byte trailer        |
+--------------------------------------------------+ EOF
```

Containers are packed back to back from offset 0 and are recognised by their
magic. The first byte sequence that is not `1.10` ends the container area.
The 8.2 data has 119 containers with 4,124 entries pointing at 3,592 distinct
frame records. A container corresponds to one animated shape (one `*.gif`
referenced from the `*.type` files); its entries are the animation frames.

### Container

| Offset | Size | Field | Notes |
|-------:|-----:|-------|-------|
| 0 | 4 | magic | ASCII `1.10` |
| 4 | 4 | count | number of entries |
| 8 | 8 x count | entries | see below |

Entry:

| Offset | Size | Field | Notes |
|-------:|-----:|-------|-------|
| 0 | 4 | offset | **relative to the container's own start offset** |
| 4 | 4 | reserved | always 0 in shipped data |

The relative addressing is easy to miss: container 0 sits at file offset 0,
so its entries look like absolute offsets and decode correctly by accident,
while every other container appears to point into the middle of pixel data.

Entries within one container may repeat (the same record used for several
animation slots), and the file contains records that no table references.
Consequently the distance to the next referenced record is only an upper
bound on a record's size. A record's real end is its trailer (see below).

### Frame record

```
+----------------------------+
| header, 24 bytes           |
+----------------------------+
| RLE rows                   |
+----------------------------+
| 0..3 zero bytes            |  pad to a 4-byte boundary
+----------------------------+
| trailer, 36 bytes          |
+----------------------------+
```

Header, `struct` format `<2H 2h 2i I I`:

| Offset | Type | Field | Meaning |
|-------:|------|-------|---------|
| 0 | u16 | `box_h` | height of the shape's full box, shared by all frames of the shape |
| 2 | u16 | `box_w1` | width of the full box **minus 1** |
| 4 | i16 | `hot_y` | hotspot row inside the box (feet of a walker, centre of an explosion) |
| 6 | i16 | `hot_x` | hotspot column inside the box |
| 8 | i32 | `dx` | x of the stored block's left edge, relative to the hotspot |
| 12 | i32 | `dy` | y of the stored block's top edge, relative to the hotspot |
| 16 | u32 | `n` | small integer, meaning unknown (often 0, `0xffffffff` or a frame-related count) |
| 20 | u32 | `flag` | small integer, meaning unknown (0, 1, -1, -2 are the common values) |

The RLE block stores only the frame's bounding box (the game crops each
frame), so the block's own width and height are **not** in the header. They
follow from decoding: height is the number of rows before the trailer, width
is the largest x reached in any row. To place the block on the shape's canvas:

```
canvas  = (box_w1 + 1) x (box_h + 1)
block_x = hot_x + dx
block_y = hot_y + dy
```

In the 8.2 data 4,118 of 4,121 decodable records fit this canvas exactly.

Placeholder records exist for empty frames: `box_h = box_w1 = 0` and/or
`dx`/`dy` set to `0x7fffXXXX` sentinels, with no RLE rows at all. A decoder
must treat these as empty frames rather than allocate from the fields.

### RLE rows

Each row is a sequence of opcodes terminated by a zero byte. `x` starts at 0
for every row.

| Opcode byte | Operands | Effect |
|-------------|----------|--------|
| `0x00` | none | end of row |
| `0x01` | `s` (1 byte) | skip `s` transparent pixels: `x += s` |
| odd, `op >= 3` | `op >> 1` pixel bytes | literal run of `op >> 1` pixels |
| even, `op >= 2` | 1 colour byte | run of `op >> 1` pixels of that colour |

A literal or colour run is therefore at most 127 pixels; longer spans are
split. Trailing transparency in a row is not encoded, so a row can end before
the block's right edge. Rows continue until the trailer; a cropped block never
ends in an empty row, so zero bytes directly before the trailer are padding.

Reference decoder for one row:

```python
def decode_row(data, p):
    """Return (spans, next_p); spans is a list of (x, bytes)."""
    x, spans = 0, []
    while True:
        op = data[p]; p += 1
        if op == 0:
            return spans, p
        if op == 1:
            x += data[p]; p += 1
        elif op & 1:
            k = op >> 1
            spans.append((x, data[p:p + k])); x += k; p += k
        else:
            k = op >> 1
            spans.append((x, bytes((data[p],)) * k)); x += k; p += 1
```

### Trailer

36 bytes, always starting on a 4-byte boundary:

| Offset | Type | Field |
|-------:|------|-------|
| 0 | 6 x f32 | `fbox[6]` |
| 24 | 6 x i16 | `box[6]` |

The floats are the shorts converted to tile units: x-like values (`box[0]`,
`box[2]`, `box[4]`) divided by 16, y-like values (`box[1]`, `box[3]`,
`box[5]`) divided by 11, matching NetStorm's 32x22 isometric tile halved.
They agree with the shorts to within about 0.1. The box appears to be a
selection or footprint rectangle and is not needed for rendering.

Because pixel data never reproduces this float/short correspondence by
chance, it is the reliable end-of-record marker: after each row, if the bytes
up to the next 4-byte boundary are zero and the 36 bytes there satisfy the
correspondence, the record ends.

### Worked example

Container 0, entry 0, record at `0x56b0b8` (168 bytes):

```
0f 00 09 00 0e 00 04 00  fd ff ff ff f2 ff ff ff  02 00 00 00 00 00 00 00
```

`box_h = 15`, `box_w1 = 9` (canvas 10 x 16), hotspot at row 14, column 4,
block at `dx = -3`, `dy = -14`. First rows:

```
01 02 04 18 00        skip 2, run 2 of colour 0x18, end of row
01 02 05 10 d3 00     skip 2, literal 0x10 0xd3, end of row
01 01 07 1f 1b d3 00  skip 1, literal 0x1f 0x1b 0xd3, end of row
```

Fifteen rows follow, the widest reaching x = 6, so the block is 6 x 15 and
is placed at column 1, row 0 of the canvas with the hotspot on its bottom
row. Two zero bytes pad to the trailer:

```
00 00 30 3f 74 d1 c5 3f 00 00 40 3f 54 82 bc 3f 00 00 00 00 8c 2e ba bd
0b 00 11 00 0c 00 10 00 00 00 ff ff
```

`box = (11, 17, 12, 16, 0, -1)`; `11/16 = 0.6875`, `17/11 = 1.545`, ... match
the floats.

### Containers are types

Each container holds the frames of one object type from the `*.type` files
(see below), in the order the game registers its types. That order is not
stored in any data file; it was recovered from the string table of the
game's `netstorm.game` binary, where the type names appear consecutively
after `zoRISING`, and verified against every container's entry count. One
name (`mog`) is absent from that table because the linker merged it with an
identical string elsewhere; it belongs at position 83. The full list of 119
file stems is `SHAPE_ORDER` in `crates/islefall-data/src/shapes.rs`.

A container's entries are the type's frames in file order, one record per
frame. If the type carries the `shadow` or `flyershadow` flag, the container
has twice as many entries: first every frame's image, then every frame's
shadow. Frames that reference the same `"file.gif" #n` share one record, and
the file contains records that no table references at all. So for a type
with N frames:

```
entries[i]       image of frame i        (0 <= i < N)
entries[N + i]   shadow of frame i       (only with a shadow flag)
```

Examples from the 8.2 data:

| Container | Type | Entries |
|----------:|------|---------|
| 0 | `dude` | 65 frames x 2 (shadowed) |
| 27 | `isle` | 317 terrain tiles, 16 x 11 |
| 63 | `sunwalker` | 66 frames x 2 |
| 88 | `priest` | 168 frames x 2 |
| 109 | `gravitationeffect` | 10 frames of a growing ring |

## `*.COL` palettes

`d/*.COL` files are 776 bytes: an 8-byte header followed by 256 RGB triplets
(768 bytes). Each is the global colour table of the GIF of the same name in
`d/`, which is how the layout was confirmed.

| Offset | Size | Field |
|-------:|-----:|-------|
| 0 | 8 | header, `08 03 00 00 23 b1 00 00` in every shipped file |
| 8 | 768 | 256 x (R, G, B) |

Most of these palettes belong to full-screen pictures (title screens, unit
portraits) and differ from each other in nearly every entry. The game's own
fixed palette, the one the `_shapes.shp` pixel indices refer to, is
`GIFCLOUD.COL`: both 512 x 512 cloud overlay images (`Gifcloud.gif`,
`Gifcloud2.GIF`) share it exactly, which only happens for images authored
in the game palette, and it renders grass green, rims orange and units in
their natural colours. Sprites use 254 of its indices (all but 252 and
255); entries 254 and 255 are pure red and cyan, presumably markers.

`d/!color.dat` is not a palette. Its 2304 bytes are nine 256-byte index
remap tables (table 4 is the identity, table 5 maps everything to 0, table
6 maps everything to 254); the others are presumably shading and
player-colour remaps applied to palette indices before drawing.

## `netstorm.tarc` text archive

`netstorm.tarc` (710,961 bytes in the 8.2 release) is a flat archive of text
resources: 124 `*.type` unit definitions, 90 `*.english` string tables and
32 `*.fort` files. It contains no images.

| Offset | Size | Field |
|-------:|-----:|-------|
| 0x00 | 10 | magic `TAFF v0.2\x1a` |
| 0x10 | 4 | 2, meaning unknown |
| 0x14 | 4 | number of files |
| 0x18 | 4 | 2, meaning unknown |
| 0x1c | 4 | 0x2c, apparently the header size |
| 0x20 | 4 | offset of the name table |
| 0x24 | 4 | length of the name table |
| 0x28 | 4 | offset of the data area |
| 0x2c | 4 x files | one u32 per file, meaning unknown |

The name table holds, per file, `u32 offset`, `u32 size`, then a
NUL-terminated path such as `\d\bird.type`. Offsets are relative to the data
area. Each file's bytes are XOR-obfuscated with the repeating 13-byte key
`mydoghasfleas`, restarting at the first byte of every file. The decoded text
is Latin-1 with `//` comments and mixed line endings.

## `*.type` unit definitions

Each `.type` file inside the archive defines one object type: a unit, a
building, an island piece, an effect or a spell. The format is a small text
language:

```
typename sunwalker constructor
typeflags walker shadow;
{
	description = "Golem";
	class = "Ground Transport";
	maxHitPoints = 50;
	theme = "sun";
	speed = 1.8;
	hotFootRatioX = 0.5;
}

// NORTH
A00 : : "golem.gif" #64 : "s_golem.gif" #64;
A05 : default gumpframe : "golem.gif" #69 : "s_golem.gif" #69;
```

Rules observed across all 124 files:

- `//` starts a comment; there are no block comments.
- `typename <name> [client] [constructor]` names the type. The modifiers
  appear on 75 files and probably select which side instantiates the type.
- `typeflags <flag>* ;` lists boolean flags. The most common are `shadow`,
  `dontSave`, `default_hotspot`, `mayDropOnRim`, `emplacement`,
  `createsisland`, `not_real`, `bomb`, `dropBlocking`, `yuckWalk`,
  `shotblocking`, `not_selectable`, `walker`, `island`, `bridge`, `altar`,
  `priest`, `geyser`. Spelling varies in case (`notreal`, `not_real`).
- One `{ ... }` block holds `key = value;` properties. Values are quoted
  strings, integers or decimals. Keys vary in case between files
  (`hotFootRatioX`, `hotfootratiox`), so lookups must be case-insensitive.
  Frequent keys: `description`, `class`, `zorder`, `foot_x`, `foot_y`,
  `theme` (`sun`, `rain`, `wind`, `thunder`), `level`, `maxHitPoints`,
  `threat`, `cost`, `range`, `speed`, `turningSpeed`, `constructionRate`,
  `group`, `techBit`, `damageEffect`, `hotFootRatioX/Y`, and sound names.
- Every other statement is a frame: `LABEL : flags : "file.gif" #n [: "file.gif" #n] ;`.
  The label is a run of letters naming an animation (`A` to `H` are the
  eight facing directions for walkers, `AA` and later letters are further
  sets) followed by the frame number. Frame flags include `default`, `help`,
  `baseframe`, `gumpframe`, and for island pieces `solid`, `dirt`, `hard`,
  `cracked`, `lit`, `unlit`. The second image reference, when present, is
  the frame's shadow. Statements may span lines and end at `;`.

Two type files carry structure in their labels:

- `isle.type` (terrain): `AA` filled pieces, `BF`/`CG`/`DH`/`EI` left, top,
  right and bottom edges, `FL`/`GM`/`HN`/`IO` outside corners clockwise
  from top-left, `AB`/`AC`/`AD`/`AE` inside corners. Each label's frames
  come in four equal blocks for the sun, thunder, wind and rain themes.
- `bridge.type`: one letter per connection pattern of a one-cell-wide
  bridge. With north, east, south and west as the connected sides: `A` all
  four, `B` N+E+S, `C` E+S+W, `D` N+S+W, `E` N+E+W, `F` E+S, `G` S+W,
  `H` N+W, `I` N+E, `J` N+S, `K` E+W, and the torn ends `L` S, `M` W,
  `N` N, `O` E. Frame number 1 (and 2) is the normal tile, 11 and 12 are
  `cracked`, 20 is `hard`. A rail is drawn along every unconnected side,
  which is how the letters were identified.

The GIF files named here are not shipped; the frames they refer to are the
records of `_shapes.shp`. How containers map to GIF names is not yet
established.

## Decoder safety notes

A misparsed `_shapes.shp` header is not a cosmetic problem. Reading two
16-bit fields as width and height and allocating a `w x h` buffer from them
can request billions of cells (a decoder written against this file did
exactly that in September 2026 and consumed 57 GB before the OOM killer
stopped it). Rules that keep a decoder safe:

- Never size an allocation from a header field. Decode the RLE into spans
  first and size the raster from what was decoded.
- Cap raster dimensions anyway (for example, refuse anything over 4M pixels
  or 2048 on a side) so a wrong guess fails with an error.
- Validate every offset against the file size and the container tables
  before dereferencing it, and bound every row walk by the record end.
- Treat placeholder records (zero box, sentinel offsets) as empty frames.
- Run exploratory decoders under a memory limit, for example
  `systemd-run --user --scope -p MemoryMax=8G -p MemorySwapMax=0 python3 tool.py`,
  so a bad parse kills the script rather than the desktop.
